# Geração .NET 10 em camadas — Gonthera CLI 2.2.2

A versão 2.2.2 inclui a reestruturação iniciada na 2.2.1 e substitui a saída .NET `_gen` por uma
solução com quatro projetos. `mainPackage` define o prefixo dos projetos e namespaces;
por exemplo, `ExampleBackend` produz:

```text
ExampleBackend.slnx
ExampleBackend.Domain/
  Generated/Entities/CustomerEntity.cs
  Generated/Enums/
  Entities/CustomerEntity.Custom.cs
ExampleBackend.Application/
  Generated/Dtos/CustomerDTO.cs
  Generated/Repositories/ICustomerRepository.cs
  Generated/Services/CustomerServiceBase.cs
  Generated/Converters/
  Generated/Common/
  Generated/Endpoints/             # contratos de entrada e saída
  Dtos/CustomerDTO.Custom.cs
  Services/CustomerService.cs
ExampleBackend.Infrastructure/
  Generated/Repositories/CustomerRepositoryBase.cs
  Generated/Data/CustomDbContext.cs
  Generated/Common/
  Generated/Messaging/             # somente quando configurado
  Generated/DependencyInjection.cs
  Repositories/CustomerRepository.cs
  Data/ApiDbContext.cs
ExampleBackend.Api/
  Generated/Controllers/CustomerControllerBase.cs
  Generated/Endpoints/             # primitives HTTP abstratos
  Controllers/CustomerController.cs
  Program.cs
static/
  properties.json
  resources.json
  postgree.sql
```

Cada projeto recebe um `.csproj` com `net10.0`. Domain não depende das outras camadas;
Application referencia Domain; Infrastructure referencia Application e Domain; Api
faz a composição das camadas. O namespace não inclui `Generated`: por exemplo,
`ExampleBackend.Domain.Entities` e `ExampleBackend.Application.Services`.

## Gerar e executar

Crie `.gonthera/project.json` e os contratos modulares conforme o README:

```json
{
  "mainPackage": "ExampleBackend",
  "projectName": "example-backend",
  "language": "DOTNET"
}
```

Execute o JAR 2.2.2 na raiz dos contratos (após construir ou obter essa versão):

```bash
java -jar gonthera-cli-2.2.2.jar --validate
java -jar gonthera-cli-2.2.2.jar
dotnet build ExampleBackend.slnx
```

Configure a conexão PostgreSQL no projeto Api, por configuração ASP.NET Core ou
variável `ConnectionStrings__Default`, antes de usar endpoints que acessem o banco:

```bash
dotnet run --project ExampleBackend.Api
```

O contexto recebe opções via DI e não depende de `DBMigrator`, `DataOnBackend` ou
classes externas de infraestrutura. O arquivo `Program.cs` inicial conecta controllers,
repositories, services e `ApiDbContext`; ele pertence ao consumidor após sua criação.
Migrations, autenticação e configurações de produção permanecem responsabilidade da aplicação.

## Código gerado e código manual

Somente as pastas `Generated` dos quatro projetos são apagadas e recriadas. Todos
os fontes nessas pastas recebem `// <auto-generated />`. Nunca personalize esses
arquivos. A pasta temporária `target/gonthera-dotnet-staging` também é descartável.

Os `.csproj`, a solução, `Program.cs`, classes customizadas e arquivos `.Custom.cs`
são criados somente quando ausentes. A regeneração preserva seu conteúdo byte a byte.
Se você excluir um desses arquivos e regenerar, o scaffold correspondente será recriado.

Entidades e DTOs são `partial`. Acrescente membros no arquivo manual:

```csharp
namespace ExampleBackend.Domain.Entities;
public partial class CustomerEntity
{
    public string DisplayName => Id.ToString();
}
```

Services e repositories têm bases abstratas geradas, com métodos `virtual`, e
implementações concretas manuais. Sobrescreva métodos nesses arquivos para mudar o
comportamento; chamar `base` reaproveita a implementação gerada. Controllers delegam
para services; conversão DTO/entity ocorre na Application. A infraestrutura mantém
as consultas, filtros e persistência no repository.

```csharp
namespace ExampleBackend.Application.Services;
public class CustomerService : CustomerServiceBase
{
    public CustomerService(ICustomerRepository repository) : base(repository) { }

    public override CustomerDTO Save(CustomerDTO input)
    {
        // Validação e comportamento específico da aplicação.
        return base.Save(input);
    }
}
```

`AddGeneratedInfrastructure` registra `ICustomerRepository` como `CustomerRepository`
e registra `CustomerService`, usando as classes concretas customizadas, nunca as bases.
O registro assume os nomes do scaffold; se renomear ou substituir classes, ajuste
os contratos e a composição de DI manualmente.

`generateDefaultControllers: false` suprime os controllers. Com `controllerAbstract:
true`, o scaffold do controller também é abstrato; crie uma implementação concreta
manual para expor as rotas. `serviceAbstract` permanece uma configuração exclusiva
do Java: no .NET sempre existe a base gerada e a implementação customizável.
`onlyDTO: true` gera somente o DTO, sem entidade, repository, service ou controller.

RabbitMQ continua opcional, na Infrastructure, com cliente 6.8.1. Configure uma
subclasse manual de `RabbitConfig` e os subscribers concretos fora de `Generated`;
registre configuração e hosted services manualmente. `AddRabbitMessaging` registra
publishers por meio de `AddRabbitMessagingGenerate(builder.Services)` quando configurados.
Primitives de endpoints customizados continuam abstratos; implemente-os na Api fora
de `Generated`. Os arquivos estáticos não são automaticamente expostos por HTTP.

## Migração e mudanças de contratos

A geração preserva a antiga pasta `_gen`; revise código manual antes de removê-la.
Atualize imports para os namespaces por camada e remova a inclusão dos fontes antigos
no build. A solução nova usa os projetos separados, não o `.csproj` monolítico antigo.

Ao remover ou renomear entidades nos contratos, as bases antigas desaparecem de
`Generated`, mas suas classes manuais são preservadas. Revise ou remova manualmente
as customizações que referenciam tipos antigos antes de compilar novamente. Arquivos
de projeto existentes também são preservados: novas referências necessárias após
mudanças de configuração devem ser incorporadas ao `.csproj` pelo consumidor.
